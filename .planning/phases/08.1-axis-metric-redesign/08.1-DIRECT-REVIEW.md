## Verdict

Phase 08.1 is directionally correct. Phase 8 failed because it treated a non-grounded coordinate frame as if it were a pole-origin metric space, then applied fixed distance thresholds to values whose units were not what the metric assumed. Removing global pole-distance severity and converting the feature to a tilt/orientation signal is the right recovery path.

However, I would not execute the current 08.1 plans as written. The high-level decision is sound, but the plans still contain enough risk to produce another superficially passing metric:

1. The schema hard break is incomplete unless all internal `coordinate_space` references are removed at the same time.
2. The Wave 0 transitional stub can silently mark unavailable axis data as `low`.
3. The proposed P90 thresholding does not actually guarantee the stated 25/25 elite-reference `low` acceptance criterion.
4. The sweep acceptance proves false-positive reduction only; it does not prove the new metric can detect a real orientation problem.

My recommendation is: proceed with 08.1, but revise the plans before execution. Treat 08.1 as an axis-distance rollback plus a conservative tilt-signal extraction, not as a validated IPSF scoring metric.

## Phase 8 Failure Summary

The inherited Phase 8 sweep found five 정은지 reference videos all classified as high severity on the axis metric:

- `ref-invert`
- `ref-climb`
- `ref-foxtop`
- `ref-foxtop-split`
- `ref-sideway-spin`

The recorded pelvis-normalized distances were approximately `2.65-3.80`, while the intended severity thresholds were around `0.15/0.30` or `0.30/0.50`, depending on document/code path. That is not a small calibration miss; it is a domain mismatch.

The important failure chain is:

1. `pose_aligned`/`pole_aligned` had no pole-origin translation.
2. `pole_aligned` rotated coordinates but did not make the pole axis pass through `(0, 0)`.
3. RTMW did not populate `keypoints_2d`, so the image-plane pole-line distance path was not available.
4. The fallback used 3D pole-aligned coordinates as if distance-to-axis were meaningful.
5. Fixed thresholds were then applied to values in the wrong coordinate semantics.

The surviving part of Phase 8 is not the distance metric. The useful parts are the already wired ForceSignals report, phase boundaries, jerk/stability/contact signals, and the raw shoulder/hip tilt observations because those are translation-invariant.

## Findings

### BLOCKER: Schema Removal Misses Existing Internal Code

08.1 plans to remove these fields from `AxisDeviationMetric`:

- `pelvis_distance_from_pole_axis`
- `chest_distance_from_pole_axis`
- `scale_denominator`
- `coordinate_space`
- `deviation_direction`

That is the right domain decision. But the current backend still references `coordinate_space` in `compute_force_signals()` warning aggregation. If the dataclass field is removed without updating that block, Phase 08.1 will introduce a runtime failure or an incomplete migration.

Required fix before execution:

- Remove or replace all backend references to the deleted fields, not just the dataclass and `compute_axis_deviation()`.
- Replace the old "all axis metrics unavailable by coordinate_space" check with a warning-based/status-based check.
- Add a regression test that calls full `compute_force_signals()`, not only `compute_axis_deviation()`.

This is the first thing I would patch into `08.1-00-PLAN.md`.

### HIGH: Wave 0 Stub Can Hide Missing Measurement

`08.1-00-PLAN.md` proposes a transitional `compute_axis_deviation()` stub that emits:

- `severity="low"`
- `confidence="low"`
- `warnings=["phase_8_1_wave_0_transitional"]`

This is acceptable only if Wave 0 is never treated as a production-quality metric. Otherwise, it turns "not measured" into "low risk", which is exactly the kind of silent semantic failure that caused Phase 8 to pass too long.

Required fix before execution:

- Do not deploy Wave 0 independently to any path that downstream analysis or Phase 9 can consume as valid severity.
- Add a top-level ForceSignals warning such as `axis_metric_transitional`.
- Ensure downstream consumers ignore axis severity when this warning is present.
- Prefer completing 08.1-00 and 08.1-01 in one release boundary.

If a stub is necessary for lockstep schema migration, it should be treated as an unavailable metric with an explicit status, not as a real `low`.

### HIGH: P90 Calibration Does Not Satisfy 25/25 Low Acceptance

`08.1-01-PLAN.md` says:

- medium cutoff = `max(reference P90, IPSF tolerance)`
- high cutoff = `medium * 1.5`

`08.1-02-PLAN.md` then says the five reference videos must produce `25/25` low axis metrics.

Those two statements do not reliably fit together. A P90 cutoff only protects the 90th percentile. With `>= medium` severity logic, values equal to or above the cutoff can become medium. Depending on percentile interpolation and sample distribution, the top reference samples may still become medium.

Required fix before execution:

- If the acceptance criterion is truly `25/25 low`, compute the medium cutoff from `max_observed_reference_tilt + margin`, not P90.
- Alternatively, change acceptance to "no high on elite references, and any medium must be manually explained", but that is a different product decision.
- Add an epsilon or strict comparison rule so a value exactly at the calibration boundary does not accidentally fail the baseline.

My preference: for this phase, use `max(P100_reference + margin, IPSF_tolerance_floor)` for the elite false-positive guard, then add negative/sensitivity tests separately so the threshold is not inflated blindly.

### HIGH: Calibration Source Must Verify Non-Null Real Tilt Values

08.1 plans to calibrate from the existing Phase 8 sweep. That is reasonable because Phase 8 already produced raw shoulder/hip tilt values before 08.1 schema migration.

The plan currently checks Firestore reachability, but reachability is not enough. It must verify that the calibration set contains real, non-null tilt values:

- 5 videos
- 5 phases per video
- 25 shoulder tilt values
- 25 hip tilt values
- no Wave 0 transitional stub values
- no values derived from distance fields

Required fix before execution:

- Add a calibration preflight that fails if any of the 25 expected phase records has null tilt.
- Persist the source sweep id, source document ids, sample count, and computed distribution in `tilt_thresholds.yaml`.
- Make the sweep evidence show both the source distribution and the final chosen thresholds.

Without this, 08.1 could calibrate from partial data or from its own transitional output.

### MEDIUM-HIGH: Tilt-Only Is Useful, But The Name Still Overclaims

The 08.1 research correctly identifies that IPSF does not provide a universal global "axis deviation" deduction and that some legitimate pole elements require the hips/body to move away from the pole.

That means the remaining shoulder/hip angle signal should not be framed as a complete axis-deviation score. It is better described as an orientation/line-angle signal that can support later technique-specific scoring.

Recommended options:

- Best: rename `AxisDeviationMetric` to `AxisTiltMetric` or `BodyLineTiltMetric`.
- Acceptable: keep the name for compatibility, but document that distance semantics were removed and severity only reflects calibrated shoulder/hip line tilt.

If the project keeps `AxisDeviationMetric`, I would explicitly state that it is not an IPSF deduction metric and not a global correctness score.

### MEDIUM: 2D Fallback Needs Undirected Angle Normalization

The proposed fallback can compute line direction in image space. This is useful if 3D pose is unavailable, but line direction is undirected. A shoulder line at `5deg` and `185deg` represents the same physical line orientation.

Required fix before execution:

- Normalize 2D angle differences modulo 180 degrees.
- Convert to the minimal unsigned angle in `[0, 90]`.
- Unit test vertical, horizontal, near-180, and swapped-keypoint cases.

Without this, the fallback may create artificial high tilt from keypoint ordering rather than body orientation.

### MEDIUM: 3D Tilt Semantics Need A Clear Definition

The current idea of using `arcsin(abs(dz) / norm)` is translation-invariant, which is why it survived the Phase 8 failure. But it measures a line's inclination relative to the pole-aligned vertical axis. It does not directly measure distance from pole or scoring correctness.

Required fix before execution:

- Document exactly what shoulder tilt and hip tilt mean after 08.1.
- Keep raw tilt values in the report even if severity is low.
- Avoid wording that implies camera-invariant or IPSF-valid correctness beyond what the metric actually proves.

This matters because a useful signal can still become misleading if named and interpreted as a score.

### MEDIUM: Sweep Needs Sensitivity Evidence, Not Only Elite Low Evidence

The 08.1 sweep acceptance currently focuses on five elite reference videos producing all low severities. That proves the false-positive problem is reduced. It does not prove the metric can catch anything.

Required additions:

- Unit-level synthetic cases above medium/high cutoff.
- At least one controlled degraded sample, amateur sample, or synthetic perturbation that should trigger medium/high.
- Evidence that `tilt_unavailable` does not count as "passed low".

This can be small. The goal is not full model validation; it is to prevent "threshold so high that nothing ever fires" from looking like success.

### MEDIUM: Phase 9 Parallelism Must Use Raw Signals, Not Severity Trust

08.1 says Phase 9 may proceed in parallel using tilt, stability, and contact. That is fine if Phase 9 treats 08.1 severity as provisional.

Required guardrail:

- Phase 9 should consume raw `shoulder_tilt`, raw `hip_tilt`, `confidence`, and warnings.
- Phase 9 should not treat `axis severity == low` as proof that line quality is correct until 08.1 sweep evidence is complete.

### LOW-MEDIUM: Sweep Script Hygiene

The proposed `sweep_phase8_1.py` is reasonable as an admin script, but I would tighten the evidence trail:

- Use millisecond timestamps if the rest of Firestore evidence uses epoch ms.
- Record git commit, backend image tag, threshold file checksum, and source sweep id.
- Clean up or lifecycle temporary `sweep_temp/` S3 copies.
- Fail the script if calibration thresholds are fallback values unless explicitly running a fallback-mode test.

These are not conceptual blockers, but they make the final evidence auditable.

## Plan-by-Plan Review

### 08.1-00: Schema Migration + Transitional Stub

Good:

- Removes the invalid distance fields.
- Forces TS/Python contract lockstep.
- Stops future consumers from seeing fake precision in distance values.

Needs revision:

- Include every existing internal reference to removed fields, especially the `compute_force_signals()` `coordinate_space` warning path.
- Add a full report construction regression test.
- Prevent the transitional stub from being consumed as real low severity.
- Add a top-level warning or status field for transitional output.

I would approve this only after the internal reference cleanup and deployment guard are added.

### 08.1-01: Tilt Algorithm + Calibration

Good:

- Uses translation-invariant signals rather than invalid distance.
- Adds a versioned YAML threshold artifact.
- Makes fallback behavior explicit.

Needs revision:

- Replace P90-based thresholding if `25/25 low` remains the acceptance criterion.
- Verify 25 non-null real tilt samples before calibration.
- Normalize 2D fallback angles.
- Add synthetic high/medium unit cases.
- Make `None -> low` impossible to mistake for measured low. It should be `low` only with low confidence and a warning, and it should be excluded from pass evidence.

I would implement this as an orientation signal first, with severity treated as conservative metadata.

### 08.1-02: Pipeline Integration + Sweep Evidence

Good:

- Re-runs the exact five known failing reference videos.
- Produces a dedicated evidence document.
- Makes the false-positive fix observable.

Needs revision:

- Add sensitivity evidence, not only elite low evidence.
- Fail if any metric is unavailable but counted as low.
- Record threshold checksum and commit/image identity.
- Separate "false-positive fixed" from "metric validity proven".

I would not accept the final sweep as sufficient if it only says `25/25 low`.

## What I Would Do

I would keep the 08.1 direction but execute it with a stricter recovery strategy:

1. Treat Phase 8 distance as deleted, not recalibrated.
   The root cause is semantic, not threshold tuning. No amount of distance-threshold adjustment fixes a coordinate frame that lacks pole-origin translation and uses mixed spaces.

2. Ship 08.1-00 and 08.1-01 as one release boundary.
   A standalone transitional stub that emits `low` is too easy to misuse. If lockstep migration requires a stub, add top-level `axis_metric_transitional` and block downstream severity consumption.

3. Calibrate elite references with `max_observed + margin`, not P90, if the product requirement is 25/25 low.
   P90 is useful for distribution reporting, but it does not match the current acceptance criterion. Keep P25/P50/P75/P90 in YAML for visibility; derive the operational cutoff from the maximum elite reference tilt plus a margin.

4. Add a minimal sensitivity suite.
   Include synthetic shoulder/hip lines above each cutoff and at least one non-reference or perturbed example. This prevents the phase from solving false positives by making the metric toothless.

5. Rename or carefully constrain the metric semantics.
   My preferred technical name is `BodyLineTiltMetric`. If renaming is too expensive, keep `AxisDeviationMetric` but explicitly document that it no longer measures distance from pole axis and is not an IPSF global deduction.

6. Let Phase 9 proceed only on raw tilt plus warnings.
   Phase 9 can use shoulder/hip tilt as a feature, but it should not interpret calibrated low severity as correctness until 08.1 evidence is complete.

## Alternative Strategies

### Recommended: Tilt Signal + Technique-Specific Scoring Later

This is the best fit for the current architecture and budget constraints.

- Phase 08.1 owns generic body-line tilt extraction.
- Phase 09 can consume tilt as one feature among stability/contact/jerk.
- Phase 11 or later owns technique-specific scoring through `GeometricCriterion`.

This avoids SMPL and avoids pretending a global pole-axis distance metric exists in the current pose pipeline.

### Conservative Contract Option: Deprecate Before Removing

If hard schema breaks are risky for stored Firestore docs or frontend consumers, keep the old distance fields for one compatibility window but always emit them as `null` with deprecation warnings.

Pros:

- Lower migration risk.
- Easier backward compatibility.

Cons:

- Keeps invalid fields visible longer.
- Requires discipline so no consumer reads them.

Given 08.1 is still pre-execution and the app appears to use axis metrics mostly by spreading/reporting rather than deeply depending on old fields, I think the hard break is acceptable as long as internal references are fixed.

### More Ambitious Option: Pole-Origin Reconstruction

A true pole-distance metric would require reconstructing pole origin/scale in the same coordinate space as the body:

- reliable pole detection,
- camera calibration or depth assumptions,
- mapping between image pole line and pose coordinates,
- scale normalization validated across camera views.

This is not appropriate for 08.1. It is a separate research phase, and it still would not become a global IPSF deduction because many valid moves intentionally move body segments away from the pole.

### Excluded: SMPL

SMPL-style body model fitting could improve 3D body geometry, but it is explicitly excluded here due to current cost constraints. It also would not solve the global-distance scoring problem by itself; the pole coordinate frame and technique-specific interpretation would still be required.

## Revised Acceptance Criteria

I would rewrite the 08.1 acceptance criteria as:

1. Phase 8 false-positive regression:
   The five known reference videos produce no high severity axis tilt metrics, no unavailable metrics counted as low, and if the business requirement remains strict, `25/25` measured phases are low.

2. Calibration integrity:
   Thresholds are derived from exactly 25 non-null shoulder/hip tilt samples from the inherited Phase 8 reference sweep, with source ids and distribution persisted.

3. Sensitivity:
   Synthetic or controlled high-tilt cases trigger medium/high severity according to thresholds.

4. Contract lockstep:
   Python dataclass, TS type, fixtures, validators, and full `compute_force_signals()` path all agree on the new schema.

5. Downstream safety:
   Transitional/unavailable tilt output cannot be interpreted as a valid low-quality score by Phase 9 or UI consumers.

## Final Recommendation

Proceed with Phase 08.1, but revise before execution.

The best recovery is not to rescue the Phase 8 distance metric. Delete it, keep raw shoulder/hip tilt as a conservative orientation signal, calibrate against elite references with a threshold rule that matches the actual acceptance criterion, and add sensitivity evidence so the new metric is not merely harmless.

If I were executing this, I would first patch `08.1-00-PLAN.md` for complete schema migration and stub gating, then patch `08.1-01-PLAN.md` for max-plus-margin calibration and 2D angle normalization, then patch `08.1-02-PLAN.md` so the final sweep proves both "elite no longer false-high" and "bad orientation can still be detected."
