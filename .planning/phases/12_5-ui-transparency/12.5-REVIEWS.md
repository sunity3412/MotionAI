## Codex Review

## Summary

Plan 12.5-01 is generally strong: it correctly narrows Phase 12.5 to result-screen transparency, fixes the prior hardcoded-weight mistake, keeps backward compatibility for old Firestore docs, and includes contract/test cleanup. The main risk is that some planned explanations may not faithfully trace to the scoring sources, especially `line` and `stability`. Since this phase is explicitly about user trust, inaccurate "why this score" copy would be worse than no copy.

## Strengths

- Clear phase fit: backend contract + result UI + mode-specific copy directly address Phase 12.5.
- Good correction from guessed `40/30/30` weights to data-driven equal weighting.
- Backward compatibility is handled with optional `dimensionExplanation`.
- `balance` drift cleanup is necessary and correctly identified.
- Mode 3 is treated as progress, not similarity, which matches the product decision.
- Test coverage is meaningfully planned across unit, contract, typecheck, fixture, and release gates.

## Concerns

- **HIGH:** `line` deficit source is under-specified and likely wrong as written. `JointAssessment.direction === "extend"` is not the same as `TechniqueProfile.expects_extension(k)`. For mode3 second+, `assessments` are previous-video angle deviations, not line-extension deficits.
- **HIGH:** `stability` explanation may drift from the actual scoring formula. `stability_score()` uses profile-aware hold windows, inter-frame diff median, `_STABILITY_TOL_DEG = 15`, and aggregate wobble. The plan mentions ad hoc thresholds like `10°`, which could produce misleading copy.
- **HIGH:** Displaying `Math.round(0.333 * 100)` for three dimensions gives `33% + 33% + 33% = 99%`, conflicting with the success criterion that displayed weights sum to 100%.
- **MEDIUM:** Adding a separate `mode` argument to `build_result` can drift from `comparison.mode`. Defaulting to `"mode1"` risks silently wrong baseline copy in tests or future call sites.
- **MEDIUM:** The plan assumes mode3 first usually has two dimensions at `50%`, but `line_score()` can return `None`; then only `stability` exists and should display `100%`.
- **MEDIUM:** Mock E2E via `pipeline.app::_process` is not actually a light mock unless Firestore, S3, adapters, signed URLs, and recognizer calls are explicitly stubbed.
- **LOW:** Current code comments still mention `4차원`, `3차원`, or `balance` in several places beyond `docs/contract.md` and `test_assemble.py`; leaving them weakens future maintainability.
- **LOW:** The roadmap example asks for deficit like `-8점`, but the plan only outputs angle difference. Either the criterion or implementation should be aligned.

## Suggestions

- Pass `profile` and `angles` into the explanation builder, or better add shared diagnostics helpers in `dimensions.py`, e.g. `line_deficits_by_joint()` and `stability_wobble_by_joint()`.
- Derive mode from `comparison["mode"]` inside `build_result`; avoid a separate `mode` parameter unless needed for tests.
- Do not round backend weights to three decimals if the UI needs exact percentages. Either display `동등 비중` or allocate display percentages so they sum to 100, e.g. `34/33/33`.
- Add edge-case tests for: no `line` dimension, one-frame stability, NaN angles, empty/unknown dimensions, and old Firestore docs without `dimensionExplanation`.
- Clarify that mode3 delta rows only render for dimensions present in `deltaFromPrevious`; angle usually has no delta row.
- Make the `_process` Mock E2E harness explicit: which functions are monkeypatched, which Firestore write is inspected, and whether no network is required.
- Extend drift cleanup to comments/docstrings in `assemble.py`, `analysis.ts`, `result.tsx`, and `simulatedResult.ts`, not just `docs/contract.md`.
- Decide whether `deficitSummary` should include point impact. If yes, use a defensible value like `100 - joint.score`; if no, remove `=-8점` from success criteria.

## Risk Assessment

**Overall risk: MEDIUM.** The implementation scope is modest and the plan is well organized, but the highest-risk part is semantic accuracy: `dimensionExplanation` must explain the same facts the scorer used. Fixing the source-of-truth issues for `line`, `stability`, and displayed weights before implementation would bring this down to LOW.
