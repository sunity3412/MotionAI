## Plan 12.5-01 Review

**Summary** - The plan is directionally correct and well-scoped for Phase 12.5: it adds a transparency layer without trying to solve scoring accuracy, and the backend -> contract -> frontend ordering is mostly sound. The main risk is that the proposed `deficitSummary` is not actually dimension-specific, so the UI may explain `line` or `stability` scores using generic joint-angle issues. That would weaken the phase's core promise: "왜 이 점수인지" should be clearer, not just more verbose.

**Strengths**
- T1/T2 correctly treat `dimensionExplanation` as a backend contract field, not frontend-only copy.
- Optional frontend field preserves compatibility with old Firestore result docs.
- T3/T4 keep scope narrow and avoid pulling in overlays, CoachCommentHook, or Phase 16 scoring work.
- T5 correctly reinforces Mode 3 as progress tracking, not similarity matching.
- T6 includes backend tests, TS typecheck, and Firestore result verification.
- T7 explicitly protects recent regressions: `letterSpacing`, Mode 3 first analysis, and playback URL renewal.

**Concerns**
- **HIGH - T1 explanation source is too generic.** `kismam.top_issues(assessments, n=1)` is joint-angle based, so it cannot honestly explain `stability` or sometimes `line`. A low stability score could end up with a knee-angle deficit as the stated reason.
- **HIGH - Contract/test drift is already present.** Current `docs/contract.md` and `backend/tests/test_assemble.py` still reference `balance`/4 dimensions, while app/backend constants use only `angle | line | stability`. T2 says "contract update," but does not explicitly clean this stale drift.
- **HIGH - Existing exact-key backend test will fail.** `test_result_has_exact_contract_keys` asserts the exact result keys, so adding `dimensionExplanation` requires test migration, not just new tests.
- **MEDIUM - Weight copy may be wrong in Mode 3.** The plan says `1.0 / len(dimension_scores)`, but T3 also says "3차원 모두 33%." Mode 3 first currently has only `line` and `stability`, so each should display 50%, not 33%.
- **MEDIUM - T5 mixes progress delta with deficit.** "지난 분석 대비 +/-N점" is progress, while `deficitSummary` explains the current score. Rendering delta "in the deficit slot" risks confusing two separate meanings.
- **MEDIUM - Mode-specific baseline is underspecified.** Backend baseline `"IPSF Code of Points + 정은지 측정값 기준"` fits Mode 1 but not Mode 3 first, which has no champion reference.
- **LOW - T6 mock E2E is underspecified.** It should name the entrypoint/script and assert all three mode states: Mode 1, Mode 3 first, Mode 3 second+.
- **LOW - Fixtures should be updated.** `app/src/lib/simulatedResult.ts` should include representative `dimensionExplanation` data so UI can be reviewed without waiting for real backend output.

**Suggestions**
- Change T1 to produce dimension-specific summaries:
  - `angle`: top joint angle deviation.
  - `line`: extension deficit from EXTEND joints, or a conservative "신전 요구 관절 기준" summary.
  - `stability`: hold-window jitter/inter-frame diff summary, not joint angle deviation.
- Add an explicit T2 subtask: remove stale `balance` references from `docs/contract.md` and backend assemble tests.
- Add tests for weight calculation with 3 dims, 2 dims, and 1 dim.
- Keep progress delta visually separate from `deficitSummary`, for example as a small "지난 분석 대비 +5점" row under the score.
- Make baseline rendering mode-aware in frontend, or include `comparisonMode`-aware copy from backend.
- Update simulated results and sample scenarios with `dimensionExplanation` so T3 can be verified locally.
- Add one old-doc compatibility test: result with no `dimensionExplanation` must render without crash.

**Risk Assessment - HIGH**

Implementation size is small, but the plan has a high trust risk if executed unchanged. The phase is about transparency, and the current T1 design can generate explanations that are not true causes of the displayed dimension scores. There is also confirmed contract/test drift around the removed `balance` dimension, which can cause avoidable breakage during implementation. Fixing those two issues would bring the plan down to MEDIUM or LOW risk.
