<objective>
Mode 1 veto/비교의 **입력 granularity** 를 "영상 통째 Gemini 업로드"에서 "DTW worst-pose
**단일 key-frame(들)** + 부위별 프롬프트 × union + N-sample"으로 교체한다. whole-video VLM 이
프레임 독립 인코딩으로 구조적으로 놓치던 **상체 결함(팔-폴 갭/고개젖힘/팔꿈치) recall 을
복구**하되 위양성은 늘리지 않는다(precision/support 게이트로 단발 환각 차단, D-08 H1). DTW
정렬 신뢰도가 낮은 정상 Mode 1 케이스(시작점/템포 상이)에서는 거짓결함을 fabricate 하지 않고
**보류 status** 로 graceful 처리한다. 정렬 신뢰도는 글로벌(distance)만이 아니라 로컬(선택 프레임
주변 path 밀도/ref-frame 존재/가시성)도 본다(D-08 H4).

**아키텍처 핵심 (D-10 HIGH-1): Gemini 호출 소유권 분리.** 23-02 가 `VisionFaultContext` 를
coach 작성 **이전에** 필요로 하므로, `_apply_vision_veto` 는 더 이상 Gemini 호출 소유자일 수
없다(아니면 Gemini 2회 호출 또는 coach 가 verdict 못 씀). 본 plan 은 호출을 두 함수로 쪼갠다 —
`_collect_vision_fault_context`(Gemini 소유, coach 전 1회) + `_apply_vision_veto(...,
vision_fault_context=...)`(Gemini 미호출, cap+audit/status 만). still 프레임 추출/정리 계약은
`SelectedFramePair` helper 로 명시한다(D-10 HIGH-2). keypoint 가시성/confidence 는 로컬 정렬과
FramePairMeasurementContext 입력이므로 vision context 수집 **전에** 산출한다(현 파이프라인은
keypoint_report 가 veto 이후에 build 됨 — app.py:2863).

**collect 시그니처 = pre-build primitive (D-12 MED-1): 임계 순서를 시그니처로 강제.** 현
파이프라인에서 result dict 는 `assemble.build_result(...)`(coach 이후, app.py:2670)에야
존재한다. 시그니처가 `_collect_vision_fault_context(score_result, ...)` 면 구현자가
`score_result["overallScore"]` 를 얻으려고 build_result 를 앞당기거나 collect 를 build 후
호출해 임계 순서(collect<coach<build_result<apply)를 깰 수 있다. numeric `overall` 은 더 이른
app.py:2442(`overall = dimensions.overall_from_dimensions(dimension_scores)`)에서 가용하므로,
시그니처를 **keyword pre-build primitive** 로 못 박는다 —
`_collect_vision_fault_context(*, overall_score: int, dimension_scores: dict, mode: str,
local_video_path: str | None, angles, profile, reference_dtw_match, reference_angles,
reference_video_path, keypoint_report, ...)`. result dict 를 받지 않으므로 build_result 를
앞당길 유인이 사라지고, ordering 테스트/trace assertion 이 "coach 전에 build_result 호출 0" 을
보장한다(D-12 MED-1). cap_would_apply 도 이 `overall_score` 로 production 동일 cap 함수에서
계산한다.

**status 의미론 (D-11 HIGH-1): cap 적용성을 pre-coach 계약에 포함.** 현 production 에서 verdict
가 `applied` 가 되는 건 `apply_downward_cap(overall, severity) < overallScore` 일 때만이다
(app.py:1729, cap=`min(overall, cap)` vision_veto.py:104-118). 즉 severity=minor/overall=88
같은 **valid 한 verdict 이 not_applicable** 이 될 수 있다(min(88,90)=88, ≮ 88). collect 가
coach 보다 먼저 도므로, cap 이 점수를 안 내리는 verdict 의 root-cause 가 coach 에 새들면
"비적용 경로 무주입" 규칙을 위반한다. 따라서 `_collect_vision_fault_context` 는 keyword
`overall_score`(numeric, build_result 무관)를 받아 **production 과 동일한** `apply_downward_cap`
으로 `cap_would_apply` 를 계산해 `VisionFaultContext` 에 노출한다(coach 주입 게이트는 23-02 가
`cap_would_apply=true` + status eligible 에서만 건다). `applied` 를 느슨히 재사용 금지 — cap 이
점수를 안 내려도 원인 코칭을 원하면 별도 status `visionFaultCandidate` 가 필요하나 기본은
cap_would_apply 게이트.

**canonical FaultKey 단일 직렬화 owner (D-17 MED-3): 어휘 drift 차단.** support 게이트가 raw
`body_part` 문자열이 아니라 canonical `FaultKey(part_scope, side, keypoint_set, fault_kind)` 로
센다(D-09 HIGH-2). 그러나 그 키가 23-03 manifest `expected_recall_keys`·result `recall_set` 과
