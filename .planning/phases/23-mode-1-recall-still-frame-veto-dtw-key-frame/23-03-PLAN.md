**어댑터 직접호출이 아니라 FULL production 경로**(`_collect_vision_fault_context`(coach 전,
Gemini 소유) → coach writers 소비 → `build_result` → `_apply_vision_veto(vision_fault_context=)`
(cap+audit, Gemini 미호출) → 캐시)를 통과해 측정한다. 프레임선별·글로벌+로컬 DTW 게이팅은
collect 가, downward cap+audit attach 는 apply 가 수행하며 verdict Gemini 호출은 1회다
(D-10 HIGH-1). (1) kip-up 상체 결함 recall 이 whole-video
baseline 대비 복구됨(스파이크 effect size 재현) — baseline 은 **동일 모델/버전으로 재실행**한
apples-to-apples, (2) 확장 케이스 매트릭스(elite clean / imperfect clean / occluded /
tempo-shifted / spinning / known-fault)에서 **위양성·alignment abstention·resource 미완을 3-way
분리** 측정해 특이도를 evaluable 입력에서 증명(D-11 HIGH-2 + D-12 HIGH-2) + arm 별 격리 cold/warm
결정론, (3) 시작점/템포 상이 케이스에서 거짓결함 비생성(보류), (4) cost/latency 게이트 +
machine-checkable pass/fail 필드를 증명·박제한다. recall 은 **프로젝트 자체 라벨셋**으로
측정하고 프롬프트는 generic 유지(known-answer 유도/curve-fit 금지, D-06).

**FP ↔ alignment abstention ↔ resource 미완 3-way 분리 (D-11 HIGH-2 + D-12 HIGH-2):
false_positive_count=0 이 specificity 를 증명하지 않는다.** clean case 가 전부
`low_alignment_confidence` 로 abstain 하거나 `resource_limited` 로 timeout 하면 분모가 비어
false_positive_count=0 이 무의미해진다. 더구나 `low_alignment_confidence`(의미적 정렬 보류)와
`resource_limited`(예산소진/샘플링 미완 = **완료실패**)는 **운영적으로 다르다** — resource_limited
를 일반 abstention 으로 세면 under-budget/timeout 구현이 clean FP 를 회피하면서 recall 의무도
부분 회피할 수 있다. 따라서 outcome class 를 분리한다(D-12 HIGH-2):
- `clean_applied_fault_count` = clean 에서 fault 잡힘(false positive).
- `clean_true_negative_count` = evaluable non-fault(none/not_applicable).
- `clean_abstention_count` = **`low_alignment_confidence` 만**(의미적 정렬 보류).
- `resource_incomplete_count` = **`resource_limited` / samplingComplete=false**(완료실패 — abstention 아님).
- `clean_evaluable_count` = applied + true_negative.
- `completion_pass` = budget-stress 아닌 모든 케이스가 samplingComplete=true AND status != resource_limited.
**main Pod gate 에서 `resource_limited` 는** manifest 가 의도적 budget-stress 케이스로 표시 안 한
한 **completion/resource coverage 를 FAIL** 시킨다 — true negative 도 alignment abstention 도
아니며 tempo-shift alignment abstention 과 **그룹화 금지**. case class 별 게이트(elite/imperfect
clean/occluded/spinning 은 manifest 가 alignment-unverifiable 로 명시 안 한 한 evaluable
non-fault 요구; tempo-shifted 는 low_alignment_confidence 허용하되 **true negative 가 아닌
ALIGNMENT ABSTENTION 으로 카운트**) + **coverage 임계**(전부 abstain → fail) + `completion_pass`
(전부 timeout → fail)로 "evaluable 입력에서 특이도 증명" 을 강제한다.

**arm 간 캐시 격리 (D-12 MED-2): cold/warm 이 서로 오염되지 않게.** production seam /
direct-adapter / whole-video baseline 이 캐시 namespace 를 공유하거나 서로 warm 시키면 cold/warm
결과가 오도된다(input_granularity / selector version / frame indices / path type 이 모두
바뀌므로 특히 중요). 따라서 `arm` ∈ {production_still, direct_adapter_still,
whole_video_baseline}; arm·cold 반복마다 `cache_namespace`/`run_id`; cold assertion = 각 arm
첫 cold run `cacheHit=false`; warm assertion = 직전 cold 와 같은 키 + `cacheHit=true`; cross-arm
assertion = whole-video baseline 키 ≠ still production 키, direct-adapter 는 manifest 가 의도
표시 안 한 한 production gate run 을 pre-warm 금지.

**타입 계약 (D-11 MED-2): to_trace_dict() 직렬화.** 런타임 trace 필드는 raw dict 가 아니라
23-01 Task 4 의 `VisionFaultContext.to_trace_dict()` 로 직렬화한다(키 drift 방지). arm/
cache_namespace/cacheHit 등 eval-only 필드는 harness 가 trace dict 에 append.

**Phase 20-04 흡수 (D-14, supersedes Phase 20-04): 본 eval 이 SEVERITY_CAP sweep 게이트를 still-frame veto 에서 OWN 한다.** 23 은 cap(50/75/90) 수식을 그대로 쓰되 veto 입력을 still-frame 으로 바꾸므로, 20-04 를 옛 whole-video 로 따로 캘리브레이션하면 23 이 다시 흔든다(중복·드리프트). 따라서 본 harness 가 still-frame 경로에서 네 게이트를 추가로 박는다: (a) **정은지 정타 95~100 retained** — elite clean case 의 최종 점수(cap 적용 후)가 95~100, 비전이 깨끗한 자세를 안 깎음, (b) **fault cap holds** — known fault row(kip-up 등)가 cap 적용으로 ≤상한(kip-up fault 영상 ≤50), (c) **score 결정론** — 같은 입력=같은 점수, cold·warm 분리(verdict 결정론과 별개로 최종 점수 byte-stable), (d) **EVAL18 baseline 변별 4쌍(power-spin/peter-pan/elbow-twist/pdshape) margin>0 퇴행 0**. case matrix·machine-checkable JSON 게이트(`elite_clean_score_in_95_100`/`fault_cap_holds`/`score_determinism_cold`/`score_determinism_warm`/`eval18_discrimination_regression_count`)·acceptance·POD checkpoint 에 포함.
