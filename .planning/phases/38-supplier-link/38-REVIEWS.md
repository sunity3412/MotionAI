# Phase 38 계획 리뷰와 Codex 의견

**판정: 실행 전 재계획 필요.** 목표와 재사용 방향은 타당하다. 그러나 현재 계획에는 정상 등록의 반환형 오류, 자기 재현성 기록의 신뢰 경계 누락, 이벤트 소비 뒤 복구 누락, 업로드 객체의 변경 가능성, 실패 사유 오분류가 있다. 이 문제를 먼저 닫아야 공급자가 올린 영상이 사람의 데이터 수리 없이 안정적으로 기준이 된다.

14개 계획과 ROADMAP의 Phase 38, CONTEXT, RESEARCH, VALIDATION, UI-SPEC을 검토했다. 핵심 소비처의 실제 코드도 대조했다. 아래는 **현재 제품에 이미 구현된 버그 전체를 감사한 결과가 아니라, 계획대로 구현했을 때 생기는 결함과 실행 위험의 리뷰**다. 구현·배포·Pod 기동은 하지 않았다.

사용자 추가 지시에 따라 각 발견에 제 의견과 개선 전략을 함께 적었다. `[확인]`은 문서·코드 또는 로컬 재현으로 확인한 사실, `[추론]`은 그 사실로부터 예상되는 실패 경로, `[미확인]`은 실서비스에서 아직 측정하지 않은 사항이다.

## 실행 전에 고칠 문제

### R1 · HIGH — `max_split()` 반환형을 잘못 소비한다

**대상:** 38-07 Task 2, action 8 (`38-07-PLAN.md:140`).

**관측 [확인]:** `features.py:265`의 `max_split()`은 `(각도, 프레임 인덱스)` 튜플을 반환한다. 기존 `extract_reference_angles.py`는 `ref_split, ref_split_idx = max_split(...)`로 푼 뒤 각도에만 `float()`와 `isfinite()`를 적용한다. 계획은 `split = max_split(...)` 이후 `round(float, 2)` 또는 None으로 적었다. 실제 함수에 `[20, 90, 70]`을 주면 `(90.0, 1)`이며, 이를 float로 바꾸면 TypeError다.

**진단 [추론]:** 계획을 문자 그대로 구현하면 정상 영상도 angles를 쓰기 전에 실패한다. 이는 Success ①의 직접 차단점이다.

**제 의견 / 수정:** 기존 스크립트와 같은 반환형 해제를 계획에 명시한다. `peak, peak_idx = max_split(...)` 뒤 유한한 peak만 저장하고, 전부 NaN이면 필드 생략 또는 None을 계약대로 처리한다. happy path 테스트에서 이 함수를 float 반환 mock으로 대체하지 말고 실제 함수를 사용한다.

### R2 · HIGH — 서버 전용 표식이라는 주장이 Firestore 규칙으로 보장되지 않는다

**대상:** 38-01 Task 2, 38-06 writer, 38-07 자기 분석 생성, 38-08 Task 1.

**관측 [확인]:** `firestore.rules:10`은 사용자가 자기 `/users/{uid}/**` 문서를 읽고 쓰도록 허용하며 필드를 제한하지 않는다. 38-08의 훅은 그 분석 문서의 `selfCheckForReference`만 읽고 Admin SDK로 해당 reference의 `selfScore`/실패 상태를 쓴다. uid와 analysis_id를 받지만 reference에 기록된 공급자·예정된 자기 분석 ID와 대조하는 동작은 없다. 38-08의 위협 표는 이 표식이 서버만 쓴다고 가정한다.

**진단 [추론]:** 공급자 권한이 없는 인증 사용자도 자기 분석 문서에 다른 새 기준 ID를 표식으로 넣으면 해당 기준의 자기 점수나 실패 상태를 바꾸는 경로를 만들 수 있다. reference 직접 쓰기 금지 규칙은 Admin 훅을 통한 쓰기를 막지 못한다. `ref-` 가드도 새 UUID 기준은 보호하지 못한다.

**제 의견 / 수정:** 권위 있는 reference 측 기록에서 `supplierUid == uid`, `selfCheckAnalysisId == analysis_id`, 현재 작업 세대가 일치할 때만 기록한다. client가 서버 전용 표식 및 관련 연결 필드를 만들거나 변경하지 못하도록 규칙도 보완한다. 성공 훅과 실패 훅에 같은 검사 함수를 쓴다. 위조 표식, 다른 공급자 ID, 과거 자기 분석 ID, 정상 사용자 분석을 테스트한다.

### R3 · HIGH — 상태를 읽고 쓰는 사이에 중복 작업이 들어올 수 있다

**대상:** 38-06 상태 writer, 38-07 Task 1/2, 38-08 Pod 라우트·requeue.

**관측 [확인]:** 38-07은 문서가 `registering`인지 읽은 다음 별도 writer로 `processing`을 쓴다. 조건부 갱신·트랜잭션·작업 소유권이 없다. 38-08의 Pod 라우트는 키 파싱 후 BackgroundTasks에 넣으며, queued 재개는 202 요청을 순차 전송하고 문서는 쓰지 않는다. 순차 HTTP 응답은 GPU 작업 완료의 직렬화를 의미하지 않는다. S3 이벤트에는 중복 전달 및 순서 변경이 가능하다. [AWS 이벤트 전달 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html).

**진단 [추론]:** 두 전달자가 동시에 같은 상태를 읽으면 등록·자기 분석을 두 번 실행할 수 있다. requeue 경로도 작업 시작 시 소유권을 획득하지 않으면 대기 문서가 다시 선택된다. 늦게 끝난 실패 작업이 이미 활성화된 기준을 failed로 바꾸는 것도 막지 못한다.

**제 의견 / 수정:** 작업 시작은 서버의 한 공통 함수에서 트랜잭션으로 처리한다. 상태뿐 아니라 작업 ID와 lease 만료 시각을 기록하고, 완료·실패 쓰기도 현재 작업 ID가 일치할 때만 허용한다. Lambda와 requeue가 같은 규칙을 사용하게 한다. 별도 큐·새 프레임워크는 필요 없다. 동시 이벤트 2개, requeue 2회, 오래된 작업의 뒤늦은 실패를 테스트한다.

### R4 · HIGH — 오류를 삼키면 등록이 복구 대상에도 남지 않는다

**대상:** 38-06 Task 2, 38-07 Task 1 (`38-07-PLAN.md:94`), 38-08 Task 2, 38-11/12 업로드 취소·재시도.

**관측 [확인]:** `_handle_reference_upload`은 절대 raise하지 않고 상태 writer마저 실패하면 로그만 남긴다. requeue 기본 대상은 queued이며 오래된 processing을 옵션으로 처리한다. 선작성 이후 presign 실패, PUT 취소·실패, 이벤트 처리 중 Firestore 장애로 남은 registering의 복구·만료 정책은 없다. UI 재시도는 새 presign부터 시작해 새 문서를 만든다.

**진단 [추론]:** SQS 메시지는 성공 소비되지만 상태 기록은 실패하면 registering 문서가 영구히 남는다. queued/processing 재개로도 찾지 못한다. 공급자는 ‘올린 영상 확인 중’을 계속 보며, 취소·재시도 때 유령 행이 늘어난다. Pod down을 정상 대기로 만드는 것과 모든 저장 장애를 성공 소비하는 것은 별개의 결정이다.

**제 의견 / 수정:** 영속 queued 기록에 성공한 경우에만 Pod 부재 메시지를 정상 소비한다. 일시적인 저장 실패는 재전달되게 한다. registering에는 업로드 만료 시각을 두고, 기존 기동/requeue 절차에서 객체 존재 여부를 확인해 미업로드 건을 종료하거나 업로드된 건을 재개한다. 자동 Pod 기동은 추가하지 않는다. ‘상태 기록 실패’, ‘presign 실패’, ‘PUT 취소’, ‘이벤트 유실 뒤 객체 존재’를 검증한다.

### R5 · HIGH — 등록 후에도 같은 업로드 URL로 기준 영상을 바꿀 수 있다

**대상:** 38-06 presigned PUT, 38-07 등록·자기 분석·활성화, 38-14 불변성 확인.

**관측 [확인]:** 계획의 presigned URL은 같은 키에 900초 동안 PUT할 수 있으며, 그 키 자체를 reference의 `videoS3Key`로 저장한다. 객체 버전·ETag·checksum을 등록 산출물과 연결하지 않는다. AWS는 만료 전 URL 재사용과 같은 키 객체 교체를 명시한다. [AWS presigned URL 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html).

**진단 [추론]:** 첫 영상으로 angles를 만든 후 같은 URL에 다른 영상을 PUT하면 기준 영상과 angles가 어긋난다. 새 이벤트는 active 상태라 스킵되지만, 재생·자기 분석은 변경된 객체를 볼 수 있다. UUID 문서 ID가 불변이어도 그 문서가 가리키는 영상은 불변이 아니다.

**제 의견 / 수정:** 업로드 완료 객체의 버전 또는 checksum을 작업에 고정하고, 공개 기준과 자기 분석이 같은 객체를 사용하도록 한다. 단순한 선택지는 임시 업로드 키와 등록 확정용 키를 분리해 확정용 키를 presign으로 쓰지 못하게 하는 것이다. 원본 업로드 변화가 처리 도중 일어나는 경우도 검출해야 한다. 같은 URL의 두 번째 PUT 후 기준 영상·angles가 바뀌지 않는 검증을 추가한다.

### R6 · HIGH — 저신뢰와 ‘서 있는 시작 없음’이 섞여 Success ②를 못 만족한다

**대상:** 38-05 Task 1, 38-07 Task 2의 6코드 합성 테스트.

**관측 [확인]:** 38-05의 판정 순서는 여러 명 → 서 있는 시작 → 저신뢰다. 기존 `hold_height.MIN_CONF`는 0.35이고, 발목 신뢰도 0.2이면 `_frame_series()`가 None이다. 따라서 계획의 `standing_start_ok`가 먼저 False가 된다. 그러나 38-07은 같은 발목 0.2 입력에서 low_confidence와 발목 목록을 요구한다. 로컬 합성 입력으로 정상 report의 바닥 산출 가능, 발목 0.2 report의 바닥 산출 불가를 재현했다.

바닥 일관성 검사 자체도 자세 분류기는 아니다. 기존 함수는 어깨~발목 세로 길이가 양수이고 이후 발이 추정 바닥 아래로 내려가지 않으면 산출할 수 있다. 합성 crouch 형태의 좌표도 그 조건을 통과했다. 이는 그 조건만으로 ‘서 있음’을 보장하지 못한다는 반례이며, 실영상 오분류율은 `[미확인]`이다.

**제 의견 / 수정:** 측정할 수 없음과 측정 결과 위반을 구분한다. 낮은 신뢰 때문에 바닥을 못 구한 입력은 low_confidence로 먼저 설명하고, 충분한 좌표가 있으나 시작 조건이 어긋난 경우만 no_standing_start로 설명한다. 서 있는 시작 판정을 바닥 일관성과 구별해 정의하고 검증한다. 기존 높이 카드의 fail-closed 성질은 그대로 유지한다. 수치 목표에 맞춰 임계값을 조정하지 않는다.

## 제가 권하는 실행 전략

현재 목표와 결정은 유지한다. 영구 보관, 두 카드, 강사 코드 표시만, 학습 기본 꺼짐, 자동 Pod 기동 제외, 기존 채점 산식 보존을 다시 협의할 필요는 없다. 실행 순서를 다음처럼 좁히는 것이 좋다.

1. **계약을 먼저 잠근다.** R1~R6을 38-01/05/06/07/08에 반영한다. 등록 작업 소유권, 업로드 객체 고정, 자기 분석 연결, 저장 실패 재전달, 시작 판정과 측정 불가의 구분을 테스트 가능한 계약으로 만든다.
2. **작은 등록 경로를 먼저 검증한다.** API 요청 → doc 선작성 → 실제 객체 → 등록 → 자기 재분석 → picker 소비까지의 입력·산출을 확정한다. 중복 이벤트·중간 저장 실패·Pod 중단·재개를 합성/로컬 테스트로 먼저 닫고, 실제 GPU 검증은 승인된 기존 Pod 세션에서 한다.
3. **호스팅 실험은 독립 진행한다.** 38-04의 사람 체크포인트가 wave 1 전체를 막아 순수 백엔드 작업까지 멈추지 않게 의존성을 분리한다. UI 전체보다 실제 폰의 로그인·파일·PUT·구독 네 가지가 되는 작은 화면으로 후보를 비교한다. 최종 후보는 기존 belle 결정 체크포인트에서 확정한다.
4. **공통 규칙과 정직한 안내를 만든다.** R7/R11/R14를 반영해 저장 선언과 실제 채점 동작, 자기 재현성과 정확도 검증을 구분한다. 두 구현 후보가 같은 순수 규칙과 데이터 테스트를 쓴다.
5. **배포 직전에 보존 증거와 복원 절차를 확보한다.** R10/R12의 baseline을 첫 쓰기 전에 찍고, 기존 리소스를 업데이트하는 경우 복원을 먼저 준비한다. 현재 계획의 changeset·실기기·Pod 승인 지점은 그대로 따른다.
6. **마지막에 독립 사용자를 확인한다.** 다른 사람이 링크로 새 동작을 등록하고 앱에서 mode1을 완료한다. 대역 계정 결과와 실제 정은지/다른 사람 검증은 완료 상태를 따로 적는다. 재현성은 같은 객체·같은 작업으로 연결된 실제 화면 점수만 보고한다.

14개 계획의 기본 구조는 유지할 수 있다. 핵심 개선은 **등록 작업이 중복·중단·재개되어도 같은 기준을 내고, 그 기준과 자기 점수를 믿을 수 있게 하는 것**이다. 이 보장을 먼저 확정하면 이후 화면·배포의 재작업을 줄일 수 있다.

| crouch 형태 합성 좌표의 계획상 바닥 통계 | 통과 — 서 있음의 충분조건이 아님 |
| 두 사람 수 fixture의 비율 | 둘 다 0.30 |

단위 함수의 사실과 계획의 충돌을 재현했으며, 아직 없는 Phase 38 구현의 전체 테스트가 통과했다고 주장하지 않는다. AWS/Firestore 라이브 공격, 실제 S3 덮어쓰기, Pod 경합, 브라우저 로그인/업로드, 실영상 시작 자세 분류는 실행하지 않았다. 웹 출처는 AWS 공식 문서만 사용했다.

## Consensus Summary

독립 외부 응답이 없어 공동 합의·리뷰어 간 이견은 산출할 수 없다. Codex의 단독 우선순위는 다음과 같다.

- **우선 수정:** R1 정상 경로 반환형, R2 서버 권위 연결, R3/R4 작업 중복·복구, R5 객체 불변성, R6 실패 분류.
- **계획 보완:** R7~R15의 표시 의미·검증 증거·배포 복원·테스트 모순.
- **유지할 방향:** 기존 추출/채점 재사용, 상태 분리, 서버 uid, 선택 동의 기본 꺼짐, 실기기 확인, 승인된 Pod 세션.
