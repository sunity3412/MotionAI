# 요약 — 강사 교정 수집 (v2 개시)

belle 승인 2건: **"강사 교정 수집을 연다"** + **"앱 안 결과 화면"**.

**판정: 됐다.** 시뮬레이터에서 입력→저장→Firestore 반영→화면 재렌더까지 실물로 확인했다.

## 어디에 붙였나 — 새 표면을 만들지 않았다

보완운동 탭의 **'강사에게 확인할 점'** 카드 안, 질문 목록 바로 아래 한 행이다.

그 자리를 고른 이유:
- **질문이 이미 거기 있다.** 백엔드가 감점마다 `coachQuestion` 을 만들어 그 카드에
  띄우고 있었다. 질문 밑에 답을 받는 것이 의미상 정확하다.
- **belle 09-09 규율과 맞는다** — "중복 표면은 옮기지 말고 지운다". 경쟁하는 새 카드를
  만들지 않고 있는 카드를 늘렸다.
- 코드가 이미 이 자리를 v2 로 예약해 뒀다: *"강사 입력 필드(coachComment /
  reviewedBy)는 v2"* (`result.tsx` D-06 주석).

## 왜 인증/엔드포인트/규칙 변경이 0인가

**강사가 학생 폰에 직접 입력한다** — 학원에서 강사가 옆에 서서 봐주는 실제 모습 그대로다.
그래서 쓰는 주체가 학생 세션이고, 기존 규칙(`users/{uid}/**` 본인 read/write)이 그대로
성립한다. `reviewedBy` 는 신원 증명이 아니라 출처 표기(자유 입력)다.

## 저장 위치 — `result` 안이 아니라 doc 최상위

계약에 `CoachCommentHook.coachComment` 가 있지만 두 가지가 안 맞았다:
1. 그것은 **리포트 1건 단위**(D-02)인데, 현장에서 강사는 **분석 1건에 한 번** 답한다.
2. 백엔드 사후 부분갱신이 `result` 를 건드리므로 그 안에 앱이 쓴 값을 두면 덮일 위험이
   있다([[partial-field-writes-invisible-to-inmemory-doc]], 2회 재발 이력).

→ `users/{uid}/analyses/{id}.coachReview` (flat 스칼라 3개). CoachCommentHook 의
per-report 필드는 향후 강사 콘솔용으로 그대로 둔다(여전히 null).
