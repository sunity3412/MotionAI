### 1-C. 1~2인 운영에 가장 단순한 것

1. **메일에 묶인 초대**(Slack·CoachNow·Trainerize 형)가 가장 단순하다. 운영이 하는 일은 초대 생성·재발송·연장·취소 넷뿐이다. 판단할 일이 없다. (판단)
2. **자가 가입 + 게시 직전 자동 검증 게이트**(Udemy·Airbnb·CameoX)는 공급자가 수십 명 이상일 때 맞는다. 검증이 자동이어야만 운영 부담이 낮게 유지된다. (판단)
3. **지원서 + 사람 심사**(Skillshare·크몽 서비스·Cameo 초기)는 대기열과 판단 비용이 생긴다. Cameo 는 3년간 기준 미달 지원 10만 건을 받았다 [확인]. 1인 운영엔 맞지 않는다. (판단)

**어느 방식을 언제 쓰나** (관측을 모은 판단)
- **첫 화면 선택**(ClassDojo·Classroom)은 두 역할의 **인원이 비슷하고**, 각 역할이 **완전히 다른 제품 면**을 보는 경우다. 게다가 둘 다 **기관(학교)** 이 뒤에서 승인한다. 선택은 셀프로 하고 검증은 기관 관리자가 한다.
  - 그 대가도 관측된다. Classroom 은 잘못 고르면 관리자만 고칠 수 있다 [확인]. ClassDojo 는 두 역할이면 메일이 두 개 필요하다 [확인].
- **앱 분리**(Uber·YouTube Studio·Trainerize)는 공급자 도구가 무겁고 공급자 수가 많을 때 쓴다.
- **프로필 토글**(Airbnb·Instagram·크몽)은 같은 사람이 양쪽을 **자주 오가고**, 공급자 전환이 **자가 등록**이며 검증을 뒤(게시 시점)로 미룰 수 있을 때 쓴다. 검증은 Airbnb 처럼 "첫 리스팅 게시 전"에 붙는다 [확인].
- **링크·초대**(Slack·CoachNow)는 공급자가 **골라서 들어오는 소수**일 때 쓴다. 누가 공급자인지 운영이 이미 안다.
- 우리 상황에 대입하면 수강생 99%, 공급자는 골라서 모셔 오는 소수다. **링크·초대**가 맞다. 끝 그림에서 같은 사람이 양쪽을 쓰면 **Airbnb 형 토글**을 쓴다. 첫 화면 선택은 99% 에게 한 단계를 더하고, 우리 뒤에는 승인해 줄 기관도 없다. (판단)

## 3. 권한 없는 사람이 공급자 링크를 열었을 때의 화면

| 앱 | 화면·동작 | 출처 |

| **CoachNow** | 이미 쓴 초대 링크로 다시 들어와 "email already in use"가 나오면, 링크를 닫고 앱에서 그 메일로 로그인하라고 안내한다 [확인] | help.coachnow.io/en/articles/3143317 |

**요지**
- 요청 받기형(Drive·Notion)은 **주인이 요청자를 아는 경우**에만 성립한다. 주인이 보는 것은 요청자의 이름·메일뿐이다 [확인].
- 모르는 사람의 요청이 오면 우리가 가진 판단 근거도 같은 이름·메일뿐이다. 그래서 요청을 받아도 검증이 되지 않는다. (판단)
- 가장 흔한 "권한 없음"은 **본인인데 다른 계정**인 경우다. Drive 도 이 경우에 대비해 계정 확인 안내를 먼저 둔다 [확인]. 오늘 belle 에게 일어난 일도 이 경우다(38-SCENARIOS §0).

## 4. 가장 단순하고 안정적인 조합

### 4-1. 실증 (2026-10 중순, 공급자 1~몇 명)

**초대 = 메일 주소 등록, 검증 = "우리가 그 메일을 초대했나" + Google 이 확인한 메일**

1. 운영 스크립트가 초대 1건을 만든다: `메일 · 강사 코드 · 만료`. 운영 동작은 Slack 과 같은 **생성 / 재발송 / 연장 / 취소** 넷이다 [Slack 확인].
2. 공급자 페이지는 Google 로그인만 지원한다 [확인: `app/src/lib/socialAuth.web.ts` — 웹 Apple 로그인은 `apple_web_unsupported`]. 로그인 뒤 서버는 아래 순서로 판정한다.
   - (a) uid 가 이미 명단에 있다 → 홈. 토큰 상태는 보지 않는다. 다시 방문하거나 링크를 다시 눌러도 오류가 나지 않는다.
   - (b) ID 토큰의 `email`(`email_verified` 참)이 유효한 초대와 일치한다 → uid 를 명단에 넣고, 초대를 "사용됨"으로 바꾼 뒤 → 홈.
     **링크 토큰은 없어도 된다.** Slack 처럼 초대를 **메일로 조회**한다 [확인].
   - (c) 링크에 토큰이 있는데 메일이 다르다 → S2 화면: "초대받은 메일(e••••@gmail.com)로 로그인해 주세요" + [다른 Google 계정으로 로그인].
   - (d) 나머지 → S3 화면: "초대받은 분만 쓸 수 있어요" + **지금 로그인한 메일 표시** + [다른 계정으로 로그인] + 문의처 하나.
3. 신청 대기열, 요청 버튼, 알림 메일은 만들지 않는다.

**이 조합이 초안보다 단순한 이유**
- 토큰을 필수로 두지 않으면 "링크를 잃어버림", "링크를 남에게 넘김", "링크 만료" 경우가 대부분 사라진다. 초대 **레코드**의 만료만 남는다.
- 보안은 줄지 않는다. 판정 근거가 여전히 "초대한 메일 = Google 이 확인한 로그인 메일"이다. 토큰이 더해 주는 것은 S2 화면에 가린 메일을 보여 주는 편의뿐이다. (판단)

## 6. 초안(38-SCENARIOS §1–§2) 판정

**총평: 동의. 방향(초대가 곧 검증, 요청 절차 없음, 첫 화면 선택 없음)은 조사한 사례와 맞는다.** 아래 다섯 가지만 바꾸거나 덧붙이기를 권한다.

| 초안 | 판정 | 바꿀 것 |
|---|---|---|
| S1 메일에 묶인 초대, 첫 로그인 때 토큰과 메일 대조 | **동의 + 단순화** | 토큰을 필수에서 뺀다. **확인된 로그인 메일로 초대를 조회**한다(Slack 형, 4-1 (b)). 토큰은 S2 화면에 가린 메일을 보여 줄 때만 쓴다 |
| S2 다른 계정 | 동의 | [다른 Google 계정으로 로그인] 버튼을 반드시 둔다(Drive 형 계정 확인 [확인]). 초대할 때 "어느 Google 계정으로 로그인하실 건가요?"를 **먼저 물어 그 메일로** 만든다(Figma 실패를 막는 방법) |
| S3 모르는 사람 = "초대받은 분만" + 문의처, 대기열 없음 | **동의** | 이 화면에도 **지금 로그인한 메일 + 계정 바꾸기**를 둔다. 실제로 가장 흔한 경우는 "본인인데 다른 계정"이다(§3). 문의처는 하나만 둔다(카톡 채널이나 메일, belle 결정 = 초안 Q2) |
| S4 재방문 | 동의 + 규칙 추가 | "명단에 있는 uid 는 토큰·초대 상태와 상관없이 홈". 쓴 링크를 다시 눌러도 오류가 나지 않게 한다(CoachNow 는 이 경우 오류가 나서 따로 안내해야 한다 [확인]) |
| S7 링크 넘김 | 동의 | 메일 조회 방식이면 링크가 넘어가도 다른 메일은 (d)로 간다. 따로 처리할 것이 없다 |
| S8 만료 14일 | 동의(숫자는 선택) | Slack 은 30일에 연장·재발송이 있다 [확인]. 14일이어도 **연장·재발송 스크립트**가 같이 있으면 된다. "만료된 초대" 화면은 (c)·(d)에 합쳐도 된다. 공급자 입장에선 할 일("운영팀에 문의")이 같다 |
| S9 권한 회수 | 동의 | 초대 취소 + 명단 제거를 한 스크립트로 한다 |
| S10 학원이 강사를 초대 | 동의 | 끝 그림에 "강사 참여 요청 → 학원장 승인" 경로를 더한다(ClassDojo·Classroom 형, 4-2) |
| §2 역할 = 실증 (b) 링크, 끝 그림 (b)+(c) 토글, (a) 안 함 | **동의** | 근거를 보강한다. 첫 화면 선택을 쓰는 앱은 인원이 비슷한 역할 + 기관 승인 구조다(§2). (c)는 Airbnb 처럼 **한 계정 두 모드**로 둔다. ClassDojo·Trainerize 처럼 메일을 둘로 나누지 않는다 |

**한 줄**: belle 의 두 질문에 대한 사례의 답은 이렇다. "찾아서 초대했으면 요청은 필요 없다(Slack·CoachNow)". "모르는 사람의 요청은 1인 운영에선 검증할 수단이 없으니 받지 않는다(Drive·Cameo 반면교사)". 끝 그림에서 모르는 사람을 받을 때는 사람이 심사하지 않고 **게시 직전 자동 게이트**로 검증한다(Udemy·Airbnb).
